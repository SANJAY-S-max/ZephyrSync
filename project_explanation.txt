PART 1: PROJECT SUMMARY & ARCHITECTURE
================================================================================
ByteSync is a high-performance, local-network (LAN) file-sharing application.
It is built using a modified MERN stack:
- Database: Neon PostgreSQL (replacing MongoDB for better relational data integrity)
- Backend: Express.js (Node.js framework)
- Frontend: React.js (Bootstrapped with Vite, styled with TailwindCSS v4)
- ORM: Prisma (Type-safe database queries)

Architecture Flow:
The app uses a client-server model but operates entirely on the Local Area Network (LAN). 
During development, the app runs on two ports (5000 for backend API, 5173 for frontend UI).
In production, the React frontend is compiled into static HTML/JS files, which 
are then served directly by the Express backend on port 5000. This means users 
only need to connect to ONE port (e.g., http://192.168.1.15:5000) to use the app.

PART 2: LIBRARIES, DEPENDENCIES, AND RESOURCES
================================================================================

--- BACKEND LIBRARIES (server/package.json) ---
1. express: The core web server framework. It handles HTTP requests (GET, POST, DELETE, PUT) and routes them to specific controllers.
2. cors: Cross-Origin Resource Sharing. A security mechanism that allows the frontend (running on a different port like 5173) to communicate with the backend (5000) without being blocked by browser security policies.
3. helmet: Secures Express apps by setting various HTTP headers (prevents XSS, clickjacking, sniffing, etc.).
4. dotenv: Loads environment variables from the `.env` file into `process.env`. Protects sensitive data like database passwords from being hardcoded.
5. prisma / @prisma/client: The Object-Relational Mapper (ORM). Translates JavaScript/TypeScript code into SQL queries for Neon Postgres. It ensures database queries are type-safe.
6. bcryptjs: A cryptographic library used to salt and hash user passwords. Salting means adding random data to the password before hashing it, preventing Rainbow Table attacks.
7. jsonwebtoken (JWT): Used to generate secure, encrypted session tokens for logged-in users. This enables "stateless" authentication.
8. multer: Middleware for handling `multipart/form-data`. It intercepts file uploads, reads the incoming byte streams, and buffers them before saving them to disk.
9. zod: A schema declaration and validation library. Used to ensure environment variables and incoming API request bodies are exactly the correct data type (e.g., ensuring an email is actually an email).
10. cookie-parser: Parses cookies attached to the client request object. Required to read the HTTP-only JWT cookies securely.
11. uuid: Generates Universally Unique Identifiers (v4) for file uploads to prevent files with the same name from overwriting each other.

--- FRONTEND LIBRARIES (client/package.json) ---
1. react / react-dom: The core library for building the User Interface using reusable components. Uses a Virtual DOM to update the UI instantly without reloading the page.
2. vite: The modern build tool and development server. It leverages native ES modules in the browser, compiling React code instantly, making it 10x to 100x faster than Create-React-App (Webpack).
3. tailwindcss / @tailwindcss/postcss: A utility-first CSS framework. We use the brand-new version 4, which uses native CSS variables instead of heavy config files, allowing for rapid UI styling directly in HTML/JSX.
4. react-router-dom: Enables client-side routing. Allows navigating between pages (like "Dashboard" and "Settings") without reloading the browser window (creating a Single Page Application - SPA).
5. axios: A promise-based HTTP client used to send GET/POST requests to the Express backend.
6. lucide-react: A beautifully designed SVG icon library. SVG icons are used instead of images because they scale perfectly without pixelation and have a very tiny file size.
7. date-fns: A library for manipulating JavaScript dates (used to display "2 hours ago" instead of raw ISO timestamps).
8. clsx / tailwind-merge: Utility functions used to conditionally merge Tailwind classes together safely without class conflicts.

PART 3: FILE-BY-FILE CODE EXPLANATION (Top to Bottom)

--------------------------------------------------
DATABASE TIER
--------------------------------------------------
File: `prisma/schema.prisma`
Explanation: This is the blueprint for the database.
- `User` model: Stores users. Contains fields for `id`, `username`, `passwordHash`, and `role` (ADMIN vs USER).
- `ServerSetting` model: A singleton table that stores the global state of the app (e.g., `permissionMode` which can be READ_ONLY, DOWNLOAD, or UPLOAD_DOWNLOAD).
- `File` model: Stores file metadata. Contains `originalName`, `storedName`, `mimeType`, `extension`, and `size`. Note: `size` uses `BigInt` because files can exceed the standard 32-bit integer limit (2GB+).
- `ActivityLog` model: Stores a history of every action taken in the app for auditing.

--------------------------------------------------
BACKEND TIER (server/src/*)
--------------------------------------------------
File: `server/src/app.ts`
Explanation: The main entry point for the backend server. 
- Lines 1-20: Imports libraries and sets up security middleware (helmet, cors, cookie-parser). Middleware are functions that run before the request hits the actual route handler.
- Lines 22-29: Defines the main API routes (`/api`) and a special `/api/server/info` route.
- Lines 24-30 (Info Route): This block uses Node's `os.networkInterfaces()` to scan the computer's hardware, filter out virtual machines, and find the exact physical WiFi IP address to show to the user.
- Lines 51-62: Starts the server listening on `0.0.0.0` (all network interfaces).

File: `server/src/controllers/auth.controller.ts`
Explanation: Handles login, logout, and session verification.
- `login()`: Searches for the username via Prisma. Uses `bcryptjs.compare()` to verify the password. If correct, uses `jwt.sign()` to create a token, and `res.cookie()` to send it back securely as an `HttpOnly` cookie (preventing Javascript from stealing it).

File: `server/src/controllers/file.controller.ts`
Explanation: The traffic cop for file uploads and downloads.
- `initUpload()`: Checks if uploads are allowed by the admin. Validates the file extension against `.env`. Creates a database record with status 'UPLOADING'.
- `uploadChunk()`: Receives a piece of a file via Multer and passes it to the `FileService`.
- `completeUpload()`: Called when all chunks are sent. Tells the service to stitch them together.
- `download()`: Finds the physical file path, creates a ReadStream, and pipes the raw bytes directly to the Express `res` (Response) object.

File: `server/src/services/file.storage.service.ts`
Explanation: Handles raw hard-drive operations.
- `saveChunk()`: Writes a piece of a file to the `storage/chunks` folder. Contains strict checks to prevent Path Traversal (stopping hackers from typing `../../../Windows/System32` in the upload path).
- `assembleFile()`: Opens a `WriteStream` to `storage/files`. Loops through every chunk in order, appends them to the new file, and deletes the temporary chunks.

--------------------------------------------------
FRONTEND TIER (client/src/*)
--------------------------------------------------
File: `client/src/main.tsx` & `App.tsx`
Explanation: The React entry point. `main.tsx` renders the `<App />` component into the HTML DOM. `App.tsx` wraps the whole application in the `<AuthProvider>` and `<BrowserRouter>`, defining which URLs load which components.

File: `client/src/context/AuthContext.tsx`
Explanation: Global State Management using React Context API.
- Replaces heavy state managers like Redux for a simpler architecture.
- On startup, `fetchSession()` uses Axios to call the backend.
- It stores the logged-in user, the server's permission mode, and the server's LAN IP address in a global state that any component can access using the `useAuth()` custom hook.

File: `client/src/pages/FileManager.tsx`
Explanation: The core file uploading screen.
- State: Uses `useState` hook to track the list of files, upload progress, and drag-and-drop state.
- `uploadFile()`: The core chunking logic. Uses JavaScript's native `Blob.slice()` method to break massive files into 4MB pieces and uses a loop to send them.

File: `client/src/index.css`
Explanation: The core styling file.
- Imports the Tailwind v4 engine using `@import "tailwindcss";`
- Under `@layer base`, it defines CSS Custom Properties (Variables).
- Contains the `.dark` class block, which flips those variables to dark mode colors instantly when the theme is toggled.

PART 4: DEEP DIVE - ADVANCED THEORETICAL CONCEPTS FOR VIVA/PRESENTATION
================================================================================
If your coordinator asks detailed technical questions, use these explanations.

A. JWT vs SESSION-BASED AUTHENTICATION
Traditional web apps store a "Session ID" in the server's RAM or database. This is bad for scalability. ByteSync uses JWT (JSON Web Tokens). 
When a user logs in, the server generates a token containing the user's ID, digitally signed with a secret key. The server DOES NOT store this token. It sends it to the browser as an `HttpOnly` cookie. On every request, the browser sends the cookie back. The server mathematically verifies the signature. This is called "Stateless Authentication" and uses less server memory.

B. ORM (PRISMA) vs RAW SQL
Writing raw SQL (`SELECT * FROM users WHERE id = 1`) is prone to SQL Injection attacks and typing errors. Prisma is an ORM (Object Relational Mapper). It allows us to write Javascript like `prisma.user.findUnique({ where: { id: 1 } })`. Prisma automatically sanitizes the inputs (preventing SQL injections) and gives us strict TypeScript auto-completion.

C. THE NETWORKING FOUNDATION & CORS
ByteSync operates using HTTP/1.1 over TCP/IP across your Local Area Network (WiFi or Ethernet). 
- Network Binding: The Express server specifically calls `app.listen(5000, '0.0.0.0')`. The '0.0.0.0' address is a special networking wildcard. It tells the Node.js server to listen on ALL available network interfaces (your WiFi card, your Ethernet adapter) rather than just `127.0.0.1` (which only listens to traffic originating from inside the laptop itself).
- CORS (Cross-Origin Resource Sharing): Configured in `app.ts` (`app.use(cors())`). This security feature ensures that if someone on your network tries to make malicious API requests to your laptop from a random website on their phone, the browser will block it. It only allows requests originating from the ByteSync UI.

D. THE UPLOAD STRATEGY (Chunked Multipart Uploads)
We cannot just send a 5GB video file in a single HTTP request. Doing so would:
1. Cause the browser to run out of RAM and crash.
2. Hit the default Express payload size limit (usually 50MB) and fail.
3. Waste hours of time if the WiFi drops for a second at 99%, forcing a total restart.

Instead, ByteSync uses "Chunking":
1. JavaScript's File API allows us to treat a file as a `Blob` (Binary Large Object).
2. The React frontend uses the `file.slice(start, end)` method to slice the 5GB file into tiny 4MB pieces instantly, without copying the file in memory.
3. We loop through these pieces, wrapping each piece in a `FormData` object.
4. Axios sends an HTTP POST request to `/api/files/upload/chunk`.
5. On the backend, the `multer` library intercepts this request, reads the raw binary buffer, and passes it to our `FileStorageService`.
6. Node.js uses `fs.promises.writeFile()` to write each 4MB chunk directly to the temporary `storage/chunks` directory.
7. Once React finishes sending all chunks, Node.js opens a `fs.createWriteStream`, loops through the chunks, and appends them into one final file in `storage/files`.

E. THE DOWNLOAD STRATEGY (HTTP Streams)
When someone wants to download a 5GB file from you, we cannot load the 5GB file into Node.js RAM and send it. It would instantly crash the server (V8 JavaScript Engine has a memory limit of about 1.4GB by default).

Instead, ByteSync uses "Streaming":
1. Express sets the `Content-Disposition: attachment` HTTP header. This tells the client browser: "Do NOT try to display this in a tab, download it as a file."
2. Node.js uses `fs.createReadStream(filePath)`. This opens the file on the hard drive but only reads a tiny buffer (about 64KB) at a time.
3. Node.js uses `readStream.pipe(res)`. This acts like a digital water hose. It reads 64KB from the hard drive, streams it directly over the WiFi via the Express `res` (Response) object, and immediately flushes it from RAM.
4. This allows 10 users to download a 5GB file simultaneously from your laptop, using almost zero RAM!
